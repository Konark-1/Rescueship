## The Pool Directory Principle

Every system has exactly one pool directory under `~/.hermes/systems/{system-name}/`. All components for that system live inside the pool. No system component lives outside its pool.

Canonical pool structure (AD-023 for sub-systems/ + core/ restructuring, AD-050 for unified AGENTS.md, AD-059 for the unified arch engine):

```
~/.hermes/systems/{system-name}/
├── AGENTS.md           # UNIFIED (AD-050): system identity + auto-generated AD/RG/cron/sub-system tables (auto-zone) + manual sections
├── _org.yaml          # Structure declaration (validatable by arch validate)

**Single Configuration doctrine (AD-011 Am.3):** each pool has exactly ONE config file — `_org.yaml` (renamed from `_org.yaml`). It declares the pool block (name/tier/category/ad_scope/parent), directories schema, service contracts, AND the `department:` block (`charter`, one-line mission; `class`: staffed | utility | dormant). Org-GLOBAL config lives in `systems/_org.yaml` (teams + defaults). The employee roster is a DERIVED cache regenerated by `axe org converge` — never hand-edit it. Channel messages are runtime logs in `systems/_org/channels.jsonl`. **`axe org converge` is the only org mutation path** (it folds dedupe + roster sync + verify); `arch emit --all` regenerates every derived render from these configs.


├── core/              # GENOMIC: state, schemas, defining logic, governance
│   ├── decisions/     # ADs about this system (AD-NNNN-[kebab-title].md)
│   ├── regressions/   # RGs about this system (RG-NNNN-[kebab-title].md)
│   └── *.py           # Defining logic (FSM, store, schemas)
├── scripts/           # All scripts for this system only
├── skills/            # Skills specific to this system only
├── data/              # Data, state, config for this system only
├── kb/                # Knowledge base (if applicable)
├── references/        # Reference docs, profiles, architecture docs
├── sub-systems/       # ALL recursive sub-pools (if any) — see AD-023
│   ├── {sub-name}/   # NATIVE sub-pool: own AGENTS.md + _org.yaml + canonical structure
│   └── {role} → …    # POOLED sub-system (AD-060): relative symlink to a foundational
│                     #   system the graduate extends (e.g. campaigns → ../../campaigns)
└── archive/           # Archived items
```

**Pooled sub-systems (AD-060):** a compass-graduate's `sub-systems/` may contain RELATIVE symlinks to foundational systems it extends — one per extended foundation CATEGORY (`{content-campaigns} → ../../{resolved}`, `{research-intelligence} → ../../{resolved}`, `{website-development} → ../../{resolved}`, `{strategy} → ../../compass/sub-systems/{resolved}`). **Categorical naming (scale rule):** architecture docs name CATEGORIES, never systems — resolve concrete names via the Foundation Category Registry (`references/foundational-system-patterns.md`), the single place system names live. **P5 exact-name rule:** the symlink name MUST equal the resolved foundation counterpart's name — never an authored alias — so the import is mechanical: `sub-systems/{foundation} → ../../{foundation}`. The foundation stays canonical (RG-028 — never copy its data); the symlink is read-only presence + discovery. Create them ONLY via `arch sub pool` (AD-060, the only write path): single symlink with an exact-name match, or `arch sub pool --pool {graduate} --sync` to auto-import every `pooled_sub_systems` entry by resolving the exact foundation name. `_org.yaml` declares `sub-systems/` with `allow_any: true`; the linter skips symlinks there (AD-042). One mechanism per relationship (P3): pooled as a sub-system → not in `services_consumed`; only called, not pooled → `services_consumed`. A pooled sub-system's AD/RG docs keep the FOUNDATION's prefix — `arch route <path>` resolves true ownership. **Foundations never pool** — they are the SOURCE of pooling; their own dependencies are plain `services_consumed`.

**AD-050 Unified AGENTS.md**: Each directory has ONE canonical document: `AGENTS.md`. It replaces the former `README.md`, `SYSTEM.md`, `SUB-SYSTEM.md`, and `_index.yaml` with:
- YAML frontmatter (machine-readable metadata for aggregation)
- Auto-generated auto-zone (AD/RG/cron/sub-system tables from frontmatter, regenerated by `arch emit --agents`)
- Manual zone (design decisions, CLI reference, notes, evolution) — preserved verbatim across re-emits

All AD/RG/cron-job files must have a `Description` field (≤1024 chars) in their frontmatter. `arch emit` aggregates these descriptions up the hierarchy so any agent can understand the full system at a glance by reading one AGENTS.md.

## Skill Symlink Topology (AD-040)

Pool-owned skills are symlinked from canonical pool sources to **pool-based** directories in `~/.hermes/skills/` — NOT semantic category directories:

```
# CORRECT — pool-based topology:
~/.hermes/skills/architecture/architecture-discipline/  →  systems/architecture/skills/architecture-discipline/
~/.hermes/skills/hermes-agent-infra/browsefleet-browser/  →  systems/hermes-agent-infra/skills/browsefleet-browser/
~/.hermes/skills/strategic-engine/polarity-map/  →  systems/strategic-engine/skills/polarity-map/

# WRONG — semantic category topology (DEPRECATED):
~/.hermes/skills/devops/architecture-discipline/  →  systems/architecture/skills/architecture-discipline/
~/.hermes/skills/career/freelance-loop/  →  systems/revenue-engine/sub-systems/freelancing/skills/freelance-loop/
```

Rules:
- Pool-owned skills MUST be at `~/.hermes/skills/{pool}/{skill}/` (symlink to canonical pool source)
- Sub-system skills follow the same pattern (link to sub-system canonical source)
- Category directories (`devops/`, `creative/`, `research/`) are only for **standalone skills** not owned by any pool
- System-integrity Tier 3 validates symlinks resolve to live pool copies

## Filesystem Governance (AD-039, AD-040, RG-033)

- `.gitignore` at `~/.hermes/` and `~/.hermes/systems/` excludes `__pycache__/` and `*.pyc`
- Frozen-dirs check is DEPRECATED — replaced by Tier 2 MD5 drift detection
- Sub-system `_org.yaml` MUST declare `sub_dirs` with `allow_any: true` for dirs containing non-standard file types
- Pool-prefixed AD/RG IDs (`DA-AD-031`, `HI-RG-022`) are distinct from bare architecture pool IDs
- `.gitignore` and `.git` tracking (RG-021) MUST be committed before `arch validate`

## ADs and RGs

**Three-tier governance (AD-022 + AD-023 + HI-AD-042):**
- **Global ADs/RGs** live in `~/.hermes/systems/architecture/core/decisions/` and `core/regressions/` — infrastructure-wide decisions (bare `AD-NNN` / `RG-NNN` IDs).
- **System-specific ADs/RGs** live in each pool's own `core/decisions/` and `core/regressions/` — decisions about that specific system (pool-prefixed IDs per AD-033, e.g. `HI-AD-038`, `DA-AD-031`).
- **Sub-system ADs/RGs** live in `{pool}/sub-systems/{sub}/core/{decisions,regressions}/` — governance scoped to a sub-pool. They INHERIT the parent pool's prefix and continue the parent pool's number sequence (AD-033) — no separate sub-system prefix. Precedents: RE-AD-001, HI-AD-036/037/039/040.
- All tiers use the same `{PREFIX}-NNN-[kebab-title].md` format and numbering.
- **CLI-visible (HI-AD-042)**: `arch` scans sub-system `core/` dirs — `arch list --pool <pool>`, `stats`, `gaps`, `related`, `update` all include sub-system docs, attributed to the parent pool. Route AD/RG reads and audits through `arch`, never raw paths.
- **The ONLY write path is `arch`** (AD-051/AD-052): `arch new/update/supersede/merge/split`, each requiring `--recon`. Never hand-create or hand-edit AD/RG files.
- Numbers are permanent — never reused, never reassigned
- Superseded ADs stay with `Status: Superseded`
- RGs are never archived — they document why prevention exists
- Each system pool's AGENTS.md auto-zone links to its relevant ADs/RGs by ID (AD-050 — formerly `README.md`/`SYSTEM.md`)

Status enum (single source of truth): `Active` · `Accepted` · `Proposed` · `Draft` · `Superseded` · `Resolved` · `Open`. Never invent parenthetical statuses — nuance goes in the body. Run `arch guide` for the full embedded rubric.

## System Registry (AD-061 — derived, never hand-maintained)

The **unified architectural registry** is `systems/architecture/data/architecture-registry.yaml` — AUTO-GENERATED from every pool's own `_org.yaml` by `arch emit --all` / `arch emit --registry`. It contains the pool registry (identity, type, tier, category, ad_scope, declared AD/RG prefixes, genome: native vs pooled symlinks, counts, description), the prefix registry (derived, no central dict), the category taxonomy, and the foundation members. The root `systems/AGENTS.md` registry table + the Foundation Category Registry table in `foundational-system-patterns.md` are also auto-generated from it.

**Zero-registration rule:** adding/renaming a system = edit its `_org.yaml` (`pool` block + `directories.core.sub_dirs.*.prefix`) + `arch emit --all`. NEVER edit core.py dicts or registry tables by hand — the linter WARNs when the registry is stale (AD-061).

## Sub-System Categories & Relationships (AD-062)

**Every sub-system (organ) MUST declare `pool.category`** from the Sub-System Category Taxonomy (`SUB_SYSTEM_CATEGORIES` in `systems/architecture/lib/core.py` — the single source; 16 categories, each mapped to a genome layer L1–L4; full table in `systems/architecture/references/sub-system-category-taxonomy.md`). The linter WARNs on missing/invalid categories; `arch sub list --category <cat>` + the registry surface them. Backfill new organs at creation (`arch sub create` scaffolds the field); categorize existing organs incrementally — WARN (not ERROR) keeps the 0/0 gate green.

**Relationships are declared ONLY as forward `relationships.depends_on`** in the organ's `_org.yaml` (targets: `system` or `system/sub-system`). Everything else is DERIVED: `depended_on_by` is an optional linter-verified mirror; `pooled_sub_systems` symlinks are implicit depends_on edges (followed via the symlink, never hand-written); reverse edges and cycles are computed from the whole graph at ORGAN granularity. `arch validate` ERRORs on any undeclared cycle; `arch sub deps [target]` renders forward + reverse edges or the full graph; `arch sub deps <target> --impact` computes the reverse transitive closure (which pools break if the target changes — system targets seed their organs). One mechanism per relationship (P3, AD-060): pooled as a sub-system → the symlink declares it; only called → `services_consumed`; semantic coupling → `relationships.depends_on`.

**Intentional feedback loops (`relationships.loops`):** a genuine bidirectional coupling (e.g. the AXE infra↔feedback loop, the campaign protocol↔seed mirror) is declared HONESTLY as a `loops` entry — which MUST also be a `depends_on` edge and MUST be agreed by both sides (the counterpart declares the same pair). The cycle detector exempts exactly the agreed pair; any cycle through an undeclared edge still ERRORs. Declaring both directions is the norm; a comment-only non-edge is the exception and must explain why (usually a one-way event channel that is not a control dependency).

## Core Principles (AD-057)

1. **Non-redundancy** — one canonical doc per concept. **AGENTS.md (AD-050) is THE canonical router+grounding doc per directory**; governance README.md files are legacy duplicates the linter flags for removal. One AD per decision, one RG per regression class (RG-010). Orphan docs (TODO-template AGENTS, unreferenced `references/*.md`, legacy `SYSTEM.md`/`SUB-SYSTEM.md`/governance README.md) are drift — `arch validate` flags them (AD-057 doc-hygiene check) and they get filled or removed, never left as traps for navigating agents.
2. **Negligible management overhead** — anything automatable is automated: arch-only AD/RG writes (AD-051/052), regenerated indexes (`arch emit`, AD-050), CLI registry integration (`arch cli sync`, AD-056), one unified surface (AD-059). Manual bookkeeping is a defect to automate, not a procedure to document.
3. **`_org.yaml` is the programmatic map** — directory structure is declared there and it is the single source for routing/validation/generation. `arch route <path>` resolves any directory to its owning pool; use it instead of filesystem spelunking.

## The Organizational Model (AXE-AD-011)

The infrastructure operates as an organization. This is structural, not metaphorical:

- **Department** = top-level system pool. The department of any cron job is its owning pool.
- **Employee** = a cron-job agent with a persistent record in `systems/autonomous-executor/data/employees.json` (`employee_id`, `name`, `role`, `department`, `home_crons`, `status`). Declared declaratively via the `employee:` frontmatter field in the job's `cron-jobs/*.md`.
- **Team** = first-class roster in `data/teams.json` (mission + members + lead). Cross-department teams must span ≥2 pools. Created ONLY via `axe org team create` (validated per AXE-RG-013) — never hand-edit teams.json.
- **AXE = collective-intelligence portal**: `axe org view|dept|employee|team|digest|sync|check` is the org surface.

**Discipline rules:**
1. Every cron job MUST have an employee record and `employee:` frontmatter — jobs without them are invisible contractors (AXE-RG-012; the smoke gate blocks the tick on this drift).
2. After ANY cron-job CRUD: run `axe org sync --write-frontmatter` (same slot as AD-027 validation).
3. Cross-department requests go through the notice board (`axe notice post --tag dept:<pool>`) or cross-dept teams — never by editing another pool's files directly.
4. New pools scaffold WITH their departmental identity: declare expected employees in `_org.yaml` (`employees:` block, advisory metadata consumed read-only by `axe org`); the AGENTS.md department roster auto-generates via `arch emit` — never hand-write it.

## The Discipline Rule

**Every new file MUST be created inside a system pool, OR trigger the creation of a new system.**

The generic directories `~/.hermes/scripts/`, `~/.hermes/data/`, `~/.hermes/research/` are **FROZEN** for new content. No new files go there.

Before creating any file:
1. Does it belong to an existing system? → Create it in that system's pool.
2. Does it represent a new domain? → Scaffold a new system pool first, then create inside it.
3. Is it a cross-cutting utility? → It goes in `hermes-agent-infra`.
4. Is it a throwaway? → Use `/tmp/`.

This rule is enforced by RG-013 and the monthly audit.

## Pre-Design Checklist (BEFORE building ANYTHING)

1. Read `~/.hermes/systems/architecture/AGENTS.md` — know the existing systems and ADs
2. Read relevant ADs for the subsystem being modified
3. Read relevant RGs for the failure modes of that subsystem
4. Check: does your planned change contradict any AD? If so, update the AD or redesign
5. Check: does your planned change reintroduce a known RG? If so, apply the prevention measure first
6. Check: will the result live inside a system pool? If not, you need `system-design` or `system-lifecycle`
7. **Unified-genome check (AD-060 P6)**: Is this a compass-graduate (or becoming one)? Design the UNIFIED GENOME: (a) which lifecycles does it OWN → scaffold NATIVE organs (`arch sub create`); (b) which foundation CATEGORIES does it extend (content-campaigns, research-intelligence, website-development, strategy) → POOL them as symlinked sub-systems (`arch sub pool {foundation} ...` or `arch sub pool --pool {graduate} --sync`), not `services_consumed`. Pooled names MUST equal the resolved foundation counterpart names exactly (P5) — resolve via the Foundation Category Registry, never hardcode names. One mechanism per relationship (P3).
7. **Foundation category check (AD-060 scale rule)**: Is this a NEW FOUNDATIONAL system (or is an existing one missing it)? It MUST declare a `category` from the Foundation Category Taxonomy in `_org.yaml` (linter-enforced) and be registered in the Foundation Category Registry. `arch pool create --tier foundational --category {cat}` scaffolds this + auto-registers. A foundation without a category cannot be classified or pooled by graduates.
7. **AXI check (AD-008)**: If the task involves creating or modifying a CLI tool, load the `axi` skill (`skill_view(name='axi')`) before building. Verify the design meets Tier 1 (Principles 4, 5, 6, 10) minimum before implementation. Use the `loo` CLI as reference implementation for Tier 3 compliance.
8. **--reason flag check (AD-032)**: If the task involves creating or modifying a CLI script that executes state mutations, side effects, or sends output, the script MUST accept a required `--reason` flag that logs the causal explanation for the action. Read-only query scripts are exempt. See AD-032 for the reference implementation pattern.
9. **Skill resolution validation (AD-034/RG-017/RG-019)**: Any cron job or skill referencing other skills must use skill names that the validator can resolve. The validator must mirror the runtime resolver (`agent/skill_utils.iter_skill_index_files`) — walking the full `~/.hermes/skills/` tree with `followlinks=True` and matching by `name:` frontmatter field, not directory path.
10. **External dependency check (RG-020)**: If the system design involves any external service (SaaS, cloud DB, managed API, third-party MCP, network-bound resource), the agent MUST confirm explicit user approval for EACH external dependency before proceeding. "Available" does not mean "authorized." Default to local-first, self-contained stores (YAML, JSON, SQLite). Present external dependencies as options with tradeoffs, never as defaults. Wait for explicit user instruction.
11. **Git tracking check (RG-021)**: Before making structural changes to any system pool, verify that `~/.hermes/` is a git repo and the target directory is tracked (`git -C ~/.hermes status --porcelain systems/`). If git is not initialized, STOP and initialize it before proceeding. Without version control, no structural change is safe. Verify `hermes-autocommit.timer` is active.
12. **Pool directory file-format linter check (RG-027/AD-061)**: Every directory declared in `_org.yaml` MUST specify a file-format constraint: either `suffix` (string or list, e.g., `suffix: [.py, .sh]`), `pattern` (glob like `*/SKILL.md`), or `allow_any: true`. A directory with `required: false` and no format constraint is a violation. Scripts directories should use `suffix: [.py, .sh]` to support both Python and shell scripts. The linter enforces BOTH directions: (a) undeclared directories (dirs on disk not in the `directories:` block) and (b) declared dirs without any format rule — `arch validate` flags both as WARNs. This is the routing contract for pooling (AD-060): a graduate reads the foundation's `_org.yaml` as its map, so foundations must declare their entire exposed surface (organs, sub-sub-systems, cron-jobs/, lib/, bin/, mcp/, audit/, …) at every depth (AD-061 push contract). Run `arch validate --pool <pool>` before and after structural changes.

## Post-Decision Checklist (AFTER building)

1. Update-before-create: scan existing docs before creating new. If an existing AD/RG covers >50% of the new content, update it in place
2. New AD needed? If a design decision with trade-offs was made AND no existing AD covers it, write a new AD (use `decision-logging` leaf → `arch new --type ad`)
3. New RG needed? If something broke AND no existing RG covers this failure mode, write a new RG (use `regression-logging` leaf → `arch new --type rg`)
4. Regenerate derived state via `arch emit --all` (agents + registry) — never hand-edit (AD-050/AD-061)
5. Cross-reference: add Related links to affected ADs/RGs
6. Update the pool `AGENTS.md` auto-zone (AD-050 — formerly `README.md`/`SYSTEM.md`) in the relevant pool
7. If a persistent fact was established, save to memory — but memory should reference ADs, not paraphrase them

## Zombie Pools (G9)

A pool failing structural health (`_org.yaml` missing, zero records, orphan
sub-systems) for more than one audit cycle is a **zombie**. The monthly audit
must either scaffold the missing genome or move the pool to
`archive/<name>-<date>-deprecated`. Repeating WARN cycles without action is a
discipline violation; findings auto-create an AXE kanban fix task instead of
re-warning.
